# Local-core threat model and phase ownership

25 October 2026. Scope: the local Node service, capture proxy, HTTP executor, interpreter bridge, collection runner, CLI/MCP report surfaces and workspace files. This is an implementation threat model supported by scoped tests and model review. It is not an independent security certification or a claim that every vulnerability is known.

## Trust assumptions

The local OS account, installed PacketLark application code and explicitly selected workspace are trusted. The service binds to loopback. Host/Origin/Fetch Metadata checks restrict browser use; they do not authenticate other local native processes. Multi-user or remotely hosted operation requires the P9 authenticated-server design.

Target API responses, imported document content, malformed bodies, network timing and consumer mutation are treated as untrusted inputs. Imported scripts currently execute as trusted, user-invoked automation inside a bounded interpreter. They can make HTTP requests, including local/private destinations. The complete import-review/destination-grant policy and worker architecture remain P3 release requirements. Do not interpret interpreter isolation or a passing advisory scan as approval to run hostile collections.

Credentials, saved requests, unsaved drafts, scope state and reports are separate assets. Current workspace/environment files and intentionally exported Postman collections can contain plaintext credentials. OS-keychain references and secret-safe export/migration UX remain P2 requirements; P0 redaction does not encrypt them.

## Boundaries, controls and evidence

- **Foreign website → local service.** Exact loopback Host and Origin checks, plus rejection of cross-site/same-site subresources lacking an allowed Origin context. Capture rejects browser Fetch Metadata/Origin traffic and supports native explicit forwarding. Public regressions in `tests/web.test.ts` cover foreign/null origins, different ports, rebinding Hosts, path traversal and no-Origin cross-site requests. Fetch Metadata is defense in depth for modern browsers, not local-client authentication.
- **Incoming API/capture bytes → buffers.** Studio JSON bodies are capped at 2 MiB with a ten-second input deadline; capture defaults to 4 MiB. Declared excess is rejected before waiting for bytes. Parser/header/socket admission is bounded. Capture slow-header, chunked input and partial-upload tests exercise these paths. Studio has at most 64 accepted sockets; capture defaults to 32.
- **Templates/headers/forms → outbound requests.** Variable expansion checks bytes while constructing each intermediate result, with five recursion passes and 10,000 substitutions per field/pass. Executor body default is 4 MiB, configurable from 1 byte to 50 MiB; resolved URLs are capped at 8 KiB and request headers at 64 KiB. Form values aggregate before encoding; at most 1,000 text fields are accepted and serialized multipart overhead counts. Tests in `tests/execution-boundaries.test.ts` cover expansion and multipart excess. These controls bound supported payloads; they are not a promise of constant process RSS.
- **Redirect → a different origin.** Bearer/basic Authorization, explicit Cookie, Proxy-Authorization and the configured API-key header are removed on an origin change. Same-origin authentication is preserved. Tests compare both origins, including a custom API-key header name. Arbitrarily named manual credential headers, sensitive request bodies and per-destination grants need the P2/P3 policy work; no universal secret-header inference is claimed.
- **Execution/script/transport → lifecycle owner.** One overall request deadline spans pre/post scripts and networking; interpreter events also retain a two-second local cap, 32 MiB interpreter heap and bounded bridge operations. Direct executions and collection runs share two active job slots. Health/cancel remain available. Studio shutdown aborts direct work/runs and closes connections; capture disconnect/stop releases forwards. Public lifecycle, execution and capture regressions cover these controls. Synchronous interpreter/JSON work can still delay the Node event loop; P3 workers and P5 responsiveness/load gates remain necessary.
- **Target bytes → observations and generated drafts.** Capture budgets decoded responses, corrects forwarded encoding metadata, sanitizes inspection copies before retention/subscription/inference, drops records when redaction cannot complete within its budget and isolates consumer copies. Header/query/cookie/form/JSON/echo, repeated fields, compression expansion and generated-draft seed checks are in `tests/capture-boundaries.test.ts`. This is decoded-body forwarding with bounded buffering, not raw packet recording or streaming/SSE/CONNECT support.
- **Run scopes/credentials → CLI/MCP/browser reports.** A bounded run-local registry observes marked/common credential fields, auth/query/body inputs and intermediate scope assignments. It recognizes raw, URI/form-encoded and base64 forms. Report sanitization walks string values rather than rewriting serialized JSON; one-character values cannot corrupt JSON syntax. Masking does not expand strings, projection is checked again, and generated IDs/status/timestamps and numeric statistics keep their schemas. CLI JSON/JUnit, real stdio MCP, run API and short-secret/rotation cases are covered. Malformed JSON diagnostics omit input excerpts. Unknown names, arbitrary transforms, script tampering and sensitive names/paths remain limitations; this is not general DLP.
- **Run output → history memory.** A run's compact result budget defaults to 16 MiB and counts logs, assertions, metadata and final state, not only bodies. Duplicate per-execution scope maps are discarded after advancing run state. Exhaustion stops further execution, marks omitted details/state and preserves attempt/assertion counts; it never retries remote requests. Sanitized reports carry their actual compact byte count. Completed Studio reports are evicted at 32 MiB or 20 entries; active progress names are bounded. Stress regressions include verbose scopes, masking expansion and multiple large completed reports. JSON/JUnit text formatting, JS object overhead, cookie state and browser memory are not represented by the compact-byte counter.
- **Async completion → selected draft/environment.** Stable ownership/version checks, serialized saves, environment snapshot revisions and explicit persistence conflicts prevent the reproduced cross-request and stale-environment overwrites. Sixteen browser harness cases cover the intended workflows. Durable recovery, conflict-review UX and file watching remain P1; unsaved drafts are currently memory-only.
- **Filesystem → canonical workspace state.** Canonical resources validate IDs/known structures and size; writes use exclusive 0600 temporary files, file fsync, rename, then memory update. Migration journals preflight and resume; corruption is preserved and reported. Public workspace tests inject failures and restart. Arbitrary concurrent editors can race hash-check/rename; cross-process ownership, descriptor-based filesystem hardening and stronger recovery belong to P1. Cross-platform/power-loss certification is not claimed.

## Phase-owned release risks

- **P1:** workspace leases/locking, external change reconciliation, kind/path/symlink policy, complete collection editing, tabs/history, durable drafts, backup/restore and conflict resolution. A content hash check is not an atomic filesystem compare-and-swap.
- **P2:** secure credential references and migration, OAuth/PKCE/refresh, certificate/TLS configuration, cookie lifecycle/retention controls, real files and streaming. Cookie-jar/state capacity must be profiled independently of response/report byte budgets.
- **P3:** explicit imported-script/agent destination grants, request/redirect body policy, bounded worker execution, typed scopes and pinned compatibility. Scripts must not gain extra workspace or network access merely by changing adapters.
- **P5:** independent security review, installed editor and supported-OS QA, browser accessibility/long-task tests, longer-duration/representative-load tests and target-user validation. The P0 reference fixtures do not substitute for production workloads.
- **P9/P10:** authenticated multi-user hosting, tenant isolation, database/jobs/backups, SSO/governance and cloud cost/abuse controls. The local service must not be exposed as a team server.

## Verification boundary

P0 closure means this scoped model, the agreed public regression interfaces and baseline/pressure artifacts have been completed for the supported local-core slice. It does not waive the phase-owned requirements above or authorize a stable release. See `P0_PROGRESS.md` and `verification/` for exact source revisions, commands, observed results and remaining release gates.
