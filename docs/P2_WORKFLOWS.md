# Credentials, OAuth, and HTTP workflows

Credentials are explicit references, such as `{{secret:UUID}}`, usable in bearer tokens, passwords, API keys, and request templates. Credentials are scoped to allowed HTTP origins. The Credentials dialog lists metadata and references; it never retrieves raw values. A request with inline authorization displays a plaintext disclosure because saving or exporting that request can retain its value. “Store and replace with reference” explicitly migrates that request's inline value; previously saved copies and exports need separate updates.

Session storage keeps secret values until the local server exits. OS keychain storage persists secrets on this computer. Keychain failures remain visible and do not silently fall back to plaintext storage. Creating a secret, changing allowed origins, and deleting it are separate actions. Changing origins and deleting entries require confirmation. Deleting a referenced credential makes dependent requests fail until their references are updated. Store OAuth client secrets with the “OAuth client secret” purpose and bind them to the token endpoint's origin.

For a saved resource, open Credentials and use “Migrate saved plaintext credentials.” Save pending edits first, choose Collection or Environment, enter its resource ID and allowed origins, and choose storage. “Preview migration” lists candidate field paths without displaying values. Select individual paths; session storage also requires acknowledging that references stop resolving after server exit. “Apply selected migration…” asks for explicit confirmation before replacing the selected fields. Changing resource details invalidates the review. Reviews expire after five minutes and are rejected if the saved resource changed. After applying, reload the collection or environment before editing and avoid saving an older draft over it. Historical files, backups, and exports may still contain plaintext; migration does not remove them.

OAuth supports authorization code with PKCE and client credentials. Enter the issuer, client ID, token endpoint, allowed resource origins, and scopes. Authorization code also requires an authorization endpoint; OpenID Connect requires the provider's JWKS URI. Client credentials requires a client secret reference. Authorization begins only through Connect, then “Continue authorization at provider” opens the provider. The local callback validates and completes the flow; refresh connections after returning. “Use connection” attaches its ID to the request. “Clear local tokens” and “Revoke at provider” are separate confirmed operations. Revocation errors remain visible; clearing local tokens does not claim provider revocation. Environment and account labels keep connection metadata identifiable. Inherited authorization still resolves from the nearest parent folder or collection.

Collection and folder “Edit inherited settings” provides an authorization mode selector and the same sensitive inputs, credential references, store-and-replace action, and OAuth picker as request authorization. These controls edit a detached parent settings draft; “Apply authoring action” commits that draft to the selected parent. Credential storage has no default allowed origin for a parent, so enter approved origins explicitly. Existing unsupported authorization metadata remains unchanged until a different mode is selected. Inherited variable JSON containing secret-marked or sensitive-key values starts hidden and requires confirmed reveal. Saving inline sensitive authorization or variables requires an explicit plaintext acknowledgement; references remain inert and do not read stored values.

Binary bodies use a native file picker. The browser uploads the chosen Blob to the local server and retains its selection ID in the request. Multipart fields can attach chosen files individually. The browser never submits imported filesystem paths or reads arbitrary local files. File selections are local server resources and may need to be chosen again after a server restart. Unused uploads from a stale draft are removed; a failed cleanup exposes a retry action. CA and client certificate files must be public PEM certificates of at most 256 KiB each; private keys and passphrases use credential references. Applying TLS settings waits for selected certificates to load and explicitly updates the current draft.

The Cookies dialog edits a URL's cookie using Set-Cookie syntax and displays domain/path scope. Cookie values are sensitive inputs. Clear requires confirmation. Cookies default to the session; enabling persistence requires the explicit checkbox and secure keychain storage. An unavailable secure backend produces an error rather than a plaintext cookie file.

Disabling persistence stops future saves and retains any previously saved bundle. “Forget saved cookies…” explicitly confirms removal of that bundle and persistence configuration while retaining current session cookies. “Clear all cookies…” separately clears the active jar.

Sending a request can consume an NDJSON stream with headers, progress, and completion. The UI keeps the preview bounded; a response artifact provides a complete response download. The inspector shows available timing, TLS, connection, redirect, and limit metadata. Cancellation uses the caller's AbortSignal. Optional JSON schemas can be entered for raw JSON bodies and validated before execution; unsupported or invalid schemas display errors without discarding the editor text.

## Integration hooks

`window.PacketLarkCredentialControls` and `window.PacketLarkHttpControls` are exported by the studio bundle. Both accept `{getRequest, changed, fetch?}`. `getRequest()` must return the current request object; `changed()` uses existing draft ownership and dirty tracking. Call `renderAuth(container)` and `renderBody(container)` on draft/tab render. The remaining entry points are `openManager()`, `openOAuth()`, `openTls()`, `openCookies()`, `execute(payload, {signal,onEvent})`, and `renderInspector(container,response)`.

Credential migration, file upload, and TLS application capture the request object and reject stale application after a draft switch. Independent native dialogs trap keyboard focus, restore focus on close, disable pending actions, retain values on errors, and refuse Escape while a write is pending. Existing request tabs and workspace synchronization remain owned by the application.

`verifyP2Controls(page,baseUrl)` in `scripts/check-p2-browser.mjs` runs through the existing connected Ego Page API. Its browser doubles test privacy and ownership without creating real credentials. Live API and provider flows require separate disposable integration fixtures; the double-based checks do not claim real provider or OS keychain validation.

`verifyP2RealWorkflow(page,baseUrl,targetUrl,fixtureFilePath)` exercises the integrated Studio controls against a disposable workspace and JSON echo peer. It creates its own collection and session credential, edits cookies, selects a native upload file, executes requests through the streaming transport, downloads a response artifact, and applies supported JSON schemas. Cookie persistence error retention uses a clearly marked injected 503 failure; successful credentials, uploads, executions, cookie writes, and schema checks use the real backend. Its unique collection, credential, cookie, and file selection are cleaned up on completion. The function must be run after the app's P2 wiring and APIs are available; merely exporting or compiling it is not browser acceptance evidence.

`verifyP2InheritedAuth(page,baseUrl)` in `scripts/check-p2-inherited-auth.mjs` verifies parent sensitive inputs, confirmed variable reveal and plaintext-save cancellation, real session credential replacement with explicitly entered origins, preservation of unsupported auth, and detached folder OAuth selection. OAuth metadata is doubled; settings writes and session credential storage use the real backend. It removes its own fixture collection and credential. Compilation does not count as browser acceptance.
